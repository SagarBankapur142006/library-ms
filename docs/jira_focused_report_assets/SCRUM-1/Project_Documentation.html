3. Functional Requirements (Mapped to Jira Stories)

Epic 1: User Authentication 3 Story Points
LMS-AUTH-01: Secure Login

"As a registered user (Admin, Librarian, Student), I want to log in with my credentials so that I can access my personalized dashboard and features."

Acceptance Criteria:
  • Validates email format and minimum password length (8 characters).
  • Generates a secure session token (JWT) on success.
  • Redirects to appropriate views based on role (Admin -> User Admin, Librarian -> Issue board, Student -> Search).
  • Renders clear error prompts for invalid credentials.
Epic 2: Book Management (Catalog) 7 Story Points
LMS-BOOK-01: Catalog CRUD Operations (5 SP)

"As a librarian, I want to add, edit, and remove books in the catalog so that book records are accurate."

Acceptance Criteria:
  • Input fields validation for Title, Author, ISBN, and stock copies count.
  • Ensures ISBN unique validation constraint to prevent double records.
  • Soft-deletes entries or blocks removal if books are checked out.
LMS-BOOK-02: Book Search and Filters (2 SP)

"As a member or librarian, I want to search books by title, author, or ISBN so that I can easily discover availability status."

Acceptance Criteria:
  • Features instaneous search response using input debounce filters.
  • Supports filtering lists to show only instock available titles.
Epic 4: Book Issue & Return 10 Story Points
LMS-TX-01: Issue Book (5 SP)

"As a librarian, I want to checkout books to active members so that loans are recorded."

Acceptance Criteria:
  • Verifies book inventory copies count > 0 before checkout approval.
  • Checks member status is active and total loans limit is not exceeded (max 5 books).
  • Computes due date (default 14 days) and records borrow transaction log.
LMS-TX-02: Return Book and Fee Calculation (5 SP)

"As a librarian, I want to process returns and dynamically calculate overdue penalties."

Acceptance Criteria:
  • Updates inventory count and updates transaction state to 'Returned'.
  • If returned date exceeds due date, dynamically prompts librarian with fine ($1/day).

Database Design & Schema

Relational data models, table fields, constraints, and relationships.

Entity-Relationship Diagram (ERD)

erDiagram USERS ||--o| MEMBERS : "has profile" USERS { int id PK string email UK string password_hash string full_name string role "Admin | Librarian | Student" timestamp created_at } MEMBERS ||--o{ TRANSACTIONS : "borrows" MEMBERS { int id PK int user_id FK string card_number UK string status "Active | Suspended" int books_checked_out timestamp joined_date } BOOKS ||--o{ TRANSACTIONS : "included" BOOKS { int id PK string title string author string isbn UK string genre string publisher int publication_year int total_copies int available_copies } TRANSACTIONS ||--o| FINES : "generates" TRANSACTIONS { int id PK int book_id FK int member_id FK int issued_by_user_id FK timestamp issue_date timestamp due_date timestamp return_date string status } FINES { int id PK int transaction_id FK decimal fine_amount string payment_status timestamp paid_date }

Table Schemas

1. `users` Table (Authentication & Access)

Field Type Constraints Description
id INT / SERIAL PRIMARY KEY Unique user profile reference.
email VARCHAR(150) UNIQUE, NOT NULL User credentials login email.
role VARCHAR(20) NOT NULL 'Admin' | 'Librarian' | 'Student'

2. `transactions` Table (Checkout logs)

Field Type Constraints Description
id INT PRIMARY KEY Borrow log transaction ID.
book_id INT FOREIGN KEY -> books(id) Checked out book title reference.
member_id INT FOREIGN KEY -> members(id) Borrowing member card reference.
due_date TIMESTAMP NOT NULL Calculated target return date.
Stack Overview Tech_Stack.md

Technology Stack & Directories

Tools, folder layouts, and implementation layers.

Core Technologies

  • Vite + React (TS): Scaffolder and fast-refresh bundler engine.
  • Custom Vanilla CSS: Custom glassmorphic styles and utility themes.
  • HTML5 LocalStorage: Used to model and store relational records for full browser interactivity.

Mock Data Persistence Layer

To bypass complex API setup during early demonstrations, a storage manager seeds the browser's database automatically on launch with dummy books, librarians, and borrow history.
